# monitoring_proj: мониторинг macOS на Prometheus

Пет-проект: собственный Prometheus-экспортер для MacBook (Apple Silicon), который отдаёт системные метрики, плюс стек Prometheus + Grafana в Docker и алерты в Telegram.

Идея: путь мониторинга целиком, от сбора метрик на хосте до алерта в мессенджере, на примере обычного ноутбука.

## Архитектура

```
[macOS, хост]                          [Docker]
Python-экспортер :9101  <--scrape--    Prometheus :9090
 (psutil + prometheus-client)               |
                                            +--> Grafana (план)
                                            +--> Alertmanager --> Telegram (план)
```

**Почему экспортер работает на хосте, а не в контейнере.** Docker Desktop на macOS запускает контейнеры внутри Linux-виртуальной машины. Процесс в контейнере видит железо этой VM, а не реальные CPU, батарею и датчики Mac. Поэтому экспортер запускается прямо на macOS, а Prometheus из контейнера обращается к нему по адресу `host.docker.internal:9101`.

Из этого же следует, что экспортер работает, пока включён Mac. Если Mac выключен или спит, Prometheus видит `up == 0`, и это штатное поведение.

```
monitoring_proj/

```

| Папка | Зачем |
|---|---|
| `exporter/` | Сердце проекта: сбор метрик и HTTP-эндпоинт `/metrics` в формате Prometheus. |
| `bot/` | Отдельный процесс для Telegram: команды и уведомления. Независим от экспортера, поэтому сбой одного не ломает другой. |
| `deploy/` | Конфигурация стека: Docker Compose, конфиги Prometheus, Alertmanager и Grafana. |
| `launchd/` | Описание автозапуска для macOS (аналог systemd): старт при входе в систему и перезапуск при падении. |
| `tests/` | Проверки логики без запуска всего стека, например парсинга вывода системных утилит. |

## Зависимости Python

| Библиотека | Зачем |
|---|---|
| `psutil` | Кроссплатформенный доступ к системной информации: загрузка CPU, память, swap, диски, сеть, процессы. Избавляет от ручного разбора вывода системных утилит. |
| `prometheus-client` | Официальный клиент Prometheus: создание метрик (`Gauge`, `Counter`) и встроенный HTTP-сервер, отдающий их по `/metrics`. |
| `pytest` | Запуск тестов. Пока в проекте нет тестов. |
| `ruff` | Линтер и форматтер: ищет неиспользуемый код, ошибки и нарушения стиля. |

## Метрики

Сейчас экспортер отдаёт три метрики типа Gauge (значение может расти и падать):

| Метрика | Описание |
|---|---|
| `mac_cpu_percent` | Загрузка CPU в процентах |
| `mac_ram_percent` | Процент занятой оперативной памяти |
| `mac_swap_percent` | Процент занятого swap (подкачки) |

Заметки по смыслу метрик:

- На macOS поле `free` у `psutil.virtual_memory()` почти всегда крошечное: система держит свободную память под кэш. Ориентироваться стоит на `available` и `percent`.
- Высокая RAM сама по себе не проблема. Тревожный сигнал: высокая RAM и высокий swap одновременно, потому что система уже вытесняет данные на диск.

## Запуск

Требуется macOS, Python 3, Docker Desktop.

**1. Окружение и зависимости (один раз)**

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

При каждой новой сессии терминала окружение нужно активировать заново: `source venv/bin/activate`.

**2. Экспортер**

```bash
python3 exporter/playground.py
```

Проверка: `http://localhost:9101/metrics`, в списке должны быть метрики с префиксом `mac_`. Остановка: `Ctrl+C`.

**3. Prometheus**

В другом окне терминала:

```bash
cd deploy
docker compose up
```

Проверка: `http://localhost:9090/targets`, у job `mac_exporter` должен быть статус **UP**. Данные можно посмотреть на вкладке Query, например запрос `mac_swap_percent`.

## Планы

- Grafana с провижинингом datasource и дашбордов из репозитория
- Автозапуск экспортера через launchd
- Алерты: swap, свободное место на диске, перегрев, деградация батареи, падение самого экспортера (`up == 0`)
- Alertmanager с отправкой в Telegram
- Метрики, специфичные для Apple Silicon: батарея (`ioreg`), thermal pressure и энергопотребление (`powermetrics`, требует root)
- Размер Docker-образов и контейнеров как метрика
- Ручной скрипт очистки неиспользуемых Docker-образов: сначала dry-run со списком кандидатов, удаление только после подтверждения
- Проверка доступности сети через Blackbox Exporter
- Скрипт `setup.sh` для установки одной командой
- Тесты, `ruff`, CI

## Заметки по ходу работы

- Метрики именуются `mac_<что>_<единица>`: по имени понятно, что измеряется.
- Алерты только предупреждают. Необратимые действия (удаление Docker-образов) выполняются вручную или после явного подтверждения.
- Пути в `docker-compose.yml` относительные, чтобы проект запускался на любой машине.
